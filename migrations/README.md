# Миграции компонентов

Эталонный DDL таблиц, на который рассчитаны SQL-запросы репозиториев компонентов.
Каждая поддиректория соответствует одноимённому компоненту:

| Директория     | Таблицы                                                         |
|----------------|-----------------------------------------------------------------|
| `mrauth`       | пользователи, 2FA, сессии, токены, защищённые операции, журналы |
| `mrmailer`     | сообщения рассылки                                              |
| `mrnotifier`   | уведомления, шаблоны уведомлений и их переменные                |
| `mrordering`   | пример таблицы с упорядочиванием строк                          |
| `mrqueue`      | очередь элементов, ошибки обработки, обработанные элементы      |
| `mrsettings`   | пример таблицы настроек и её журнал изменений                   |

Миграции созданы в схеме `sample_schema` с примерными именами таблиц и применяются только
как образец и в тестах библиотеки. Библиотека их не встраивает и не применяет сама.

## Использование в приложении

Компоненты встраиваются в таблицы приложения: схему и имена таблиц выбирает приложение и передаёт
их репозиториям через `mrsql.DBTableInfo`. Поэтому миграции не применяются как есть, а переносятся
в миграции приложения:

1. Скопировать нужные файлы в директорию миграций приложения и дать им номера по его порядку.
2. Заменить `sample_schema` и примерные имена таблиц на свои; те же имена передать в
   `mrsql.DBTableInfo` при сборке компонента (см. [wire](../wire)).
3. Сохранить состав и типы колонок, их ширины, ограничения `CHECK`, индексы и последовательности:
   запросы репозиториев и проверки конфигурации на них опираются. Например, лимиты длины в
   [wire/mrauth/config/validate.go](../wire/mrauth/config/validate.go) равны ширинам колонок
   `migrations/mrauth`.
4. Компоненты `mrmailer` и `mrnotifier` построены на `mrqueue`, поэтому им также нужны таблицы
   очереди из `migrations/mrqueue`.

## Использование в тестах

Интеграционные тесты репозиториев поднимают Postgres через `go-storage/mrtests/pgtest.Tester`
и применяют миграции своего компонента:

```go
ts.pgt.ApplyMigrations(ts.T(), tests.MigrationsDir("mrauth"))
```

Схема `sample_schema` перечислена в `tests.DBSchemas()`. Набор миграций каждого компонента
самодостаточен: сам создаёт схему и сам её удаляет, поэтому тест применяет только свой набор.

## Правило изменения

Миграции — часть контракта компонента. Изменение таблицы вносится сюда вместе с правкой
репозитория и связанных с шириной колонок лимитов, а приложения переносят его в свои миграции.
